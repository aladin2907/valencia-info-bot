# Valencia Info Bot — архитектура

Telegram-бот (и в будущем мобильное приложение), который отвечает на вопросы о жизни в Валенсии, опираясь на реальные обсуждения в местных чатах экспатов и проверяя факты по официальным источникам.

**Статус:** дизайн согласовывается. **Дата:** 2026-08-21.

---

## 1. Задача и её сложность

База — это **разговоры живых людей**, а не документация. Отсюда три проблемы, которые определяют всю архитектуру:

| Проблема | Пример | Решение |
|---|---|---|
| **Информация устаревает** | «Цита в консульство — за неделю» (2024) vs «теперь ждать месяц» (2026) | Слой фактов с датами жизни + гашение устаревшего (§3.3) |
| **Сказано один раз, дальше — отсылки** | Подробная инструкция в январе, потом полгода «смотри выше / в закрепе» | Денормализация родителя + слой фактов как «постоянная память» (§3.3) |
| **Релевантность ≠ похожесть** | Векторный поиск тащит «похожее по смыслу», а нужен точный ответ | Гибридный поиск + реранкер + вес свежести (§5) |

Что мы изучили: 7 open-source проектов ботов над историей чатов и системы «памяти для агентов» (Graphiti/Zep, Mem0, Letta, cognee), плюс работы по темпоральному RAG. Два главных вывода:

- **Проблему отсылок не решает ни один чат-бот** — решение есть только в системах памяти: слой извлечённых фактов с двумя временными осями. Его и берём.
- **Решение «что кого отменяет» должно принимать код, а не LLM.** К этому независимо пришли три проекта; LLM отвечает только за извлечение факта и дат.

## 2. Общая схема

```
                        ┌──────── Ночной контур (cron, ~04:00) ────────┐
   Telegram-группы ────► ingest ──► треды ──► embeddings ──► факты ────► Postgres
                        └───────────────────────────────────────────────┘

                        ┌──────── Контур ответов (24/7) ───────────────┐
   Telegram-бот ──┐                                                     │
                  ├──► API (FastAPI) ──► агент (LangGraph) ──► Postgres │
   Мобильное  ────┘                            ├──► модели на сервере   │
   приложение                                  │    (эмбеддинги, реранкер)
                        └────────────────────  └──► LLM + Perplexity ───┘
```

Ядро — **отдельный сервис с HTTP API**, а не логика внутри бота. Telegram-бот — первый клиент, мобильное приложение — второй; оба ходят в один эндпоинт `POST /ask`. Это решение принято сразу, чтобы не переписывать ядро при добавлении приложения.

## 3. Хранение

Три слоя, каждый со своей ролью и своим сроком жизни.

### 3.1. `messages` — сырой архив (неприкосновенный)

Всё, что скачано из Telegram, слово в слово. Никогда не редактируется и не удаляется — это источник правды, из которого в любой момент можно пересобрать всё остальное.

```sql
messages (
  group_slug text, message_id bigint,          -- PRIMARY KEY (group_slug, message_id)
  sender_id bigint, sender_name text,
  text text, entities jsonb,                   -- ссылки/упоминания из Telegram
  reply_to_message_id bigint,                  -- топология ответов
  sent_at timestamptz, edited_at timestamptz,
  tg_link text,                                -- https://t.me/c/<chat>/<id> — кликабельная цитата
  raw jsonb                                    -- исходный объект целиком
)
```

*Почему так:* переиндексация, смена модели эмбеддингов, изменение логики сборки тредов — всё это делается пересчётом из архива, без повторного скачивания Telegram.

### 3.2. `threads` — треды (основная единица поиска)

Диалог = корневое сообщение + все ответы. Именно тред ищется и уходит в LLM: одно сообщение вне контекста бесполезно («да, там дорого» — где?).

```sql
threads (
  id bigserial PK,
  group_slug text, root_message_id bigint,     -- UNIQUE (group_slug, root_message_id)
  content text,                                -- "Имя: текст" построчно
  message_count int,
  started_at timestamptz,                      -- первое сообщение
  last_activity_at timestamptz,                -- ПОСЛЕДНИЙ ответ — по нему считается свежесть
  content_hash text,                           -- sha256; изменился → переэмбеддить
  tsv tsvector GENERATED,                      -- полнотекстовый поиск (russian + simple)
  tg_link text, metadata jsonb
)
threads_embeddings (                           -- отдельная таблица-«проекция»
  thread_id FK ON DELETE CASCADE,
  model text, dimensions int,                  -- можно держать две модели параллельно
  source_hash text,                            -- от какого текста посчитан
  embedding vector(1024),
  status text, attempt_count int, last_error text   -- очередь пересчёта с ретраями
)
```

Два решения, подсмотренные у лучших проектов:

- **Свежесть = дата последнего ответа, а не создания.** Тред, где отвечают сегодня, живой, даже если начат год назад (так делает Onyx).
- **Эмбеддинги — в отдельной таблице.** Смена модели, сбой модели, переиндексация не трогают данные; строки с `status='pending'` просто пересчитываются ночью. Модель — self-hosted `BAAI/bge-m3` (1024 измерения, окно 1024 токена), крутится на том же сервере; замер — в [QUALITY.md](QUALITY.md).

**Отсылки на родителя решаются на этапе индексации:** в текст, который эмбеддится, подмешивается контекст — тема треда и текст сообщения, на которое отвечают. Это дешёвый приём, дающий заметный прирост качества.

### 3.3. `facts` — извлечённые факты (память с историей)

Слой, который отвечает за устаревание и за отсылки. Ночью из новых тредов LLM вытаскивает конкретные утверждения — «в консульство запись открывается за месяц», «Mercado Central работает 07:30–15:00».

```sql
facts (
  id bigserial PK,
  topic text,                                  -- 'nie', 'schools', 'consulate', ...
  statement text,                              -- сам факт, одной фразой
  embedding vector(1024),
  valid_from timestamptz,                      -- с какого момента факт верен В МИРЕ
  invalid_at timestamptz,                      -- когда перестал быть верен (NULL = актуален)
  superseded_by bigint REFERENCES facts(id),   -- какой факт его заменил
  confidence real,
  source_thread_ids bigint[],                  -- откуда взято — для цитат и проверки
  created_at timestamptz                       -- когда СИСТЕМА об этом узнала
)
```

**Две оси времени** (модель Graphiti/Zep, у них 30k звёзд на GitHub): «когда факт был верен в реальности» и «когда мы о нём узнали» — это разные вещи, и без их разделения нельзя корректно отвечать «а как было летом».

**Гашение устаревшего — решение принимает код, а не LLM.** Три независимых проекта (Graphiti, cognee, MemStrata) сошлись на одном: LLM извлекает факт и даты, но *кто кого отменяет* решается детерминированно по датам. Так же делаем и мы:

1. LLM извлекает факт и переводит относительные даты в абсолютные («с сентября» → `2026-09-01`), опираясь на дату треда.
2. Новый факт сверяется с близкими старыми **внутри одного ключа** (см. ниже).
3. Победитель — по датам, арифметикой. Проигравший получает `invalid_at` и `superseded_by`. Ничего не удаляется.

**Ключи-темы вместо «похожести».** Важное предупреждение из исследования: близость эмбеддингов **не отличает противоречие от дополнения** (точность на уровне монетки). Поэтому гасим не «похожие» факты, а факты с одинаковым ключом: `(NIE, стоимость пошлины)`, `(empadronamiento, срок записи)`, `(школа X, цена комедора)`. Начинаем с 10–20 ключей по самым частым вопросам; всё, что вне списка, просто сосуществует и уходит в ответ с датами.

**Отсылки решаются через provenance.** Факт хранит `source_thread_ids` — и в ответ уходит **исходный тред целиком**, а не вырванная фраза. Короткая реплика «смотри выше» находится по смыслу, а пользователь получает ту самую подробную январскую инструкцию. Повторное упоминание факта не создаёт дубль, а добавляет ещё один `thread_id` — заодно это счётчик подтверждений: чем больше людей подтвердили, тем выше доверие.

**Устаревшее не прячем, а показываем с датами.** Если по теме есть и старый, и новый факт, в промпт уходят оба со сроками действия — модель тогда скажет «в марте 2025 писали про 60 €, в мае 2026 — про 80 €» вместо тихой выдачи неверной цифры.

### 3.4. `users` — пользователи и лимиты

`id, platform, username, language_code, next_allowed_message_at, message_count_today, created_at` — как в старой `users_valencia`, но с полем `platform` (telegram / ios / android).

## 4. Наполнение (ночной контур)

Один cron-запуск в сутки, шесть шагов:

1. **Докачка.** `valencia_telegram_ingest` (Telethon) забирает сообщения с момента прошлого запуска → `messages`.
2. **Пересборка тредов за хвост.** Не только вчерашние: тред живёт несколько дней, на старый вопрос отвечают сегодня. Пересобираем все треды, затронутые новыми сообщениями (окно ~14 дней) → `upsert` по `(group_slug, root_message_id)`.
3. **Эмбеддинги.** Только там, где изменился `content_hash`. Считает своя модель на сервере; очередь с ретраями — сбой не роняет весь прогон.
4. **Извлечение фактов** из новых/изменившихся тредов (LLM, батчами) с абсолютизацией дат по дате треда.
5. **Разрешение противоречий.** Только в окрестности затронутых тем, не по всему корпусу. Шаг «советующий»: если он упал, ingest не считается проваленным — факты остаются, гашение доедет следующей ночью.
6. **Отчёт.** Строка в лог + уведомление в Telegram: сколько сообщений, тредов, фактов, сколько ошибок.

Прогон идемпотентный: упал на середине — перезапуск догоняет, дублей не будет (всё через `upsert` по естественным ключам).

Ожидаемый объём: 50–200 новых тредов за ночь. Эмбеддинги считаются своей моделью на сервере и стоят только процессорного времени (минуты на такой объём); платный тут только шаг извлечения фактов — ~$0.2–1 в сутки.

## 5. Ответы (контур 24/7)

Агент на LangGraph, восемь шагов. Промпты переносятся дословно из старого n8n-workflow (сохранён в `reference/n8n/rag-flow.json`).

```
1. rate_limit      кулдаун 5 минут между вопросами (таблица users)
2. optimize_query  GPT-4.1: чистка вопроса, ключевая фраза сразу на ru+uk,
                   плюс извлечение временного фильтра («что писали летом»)
3. retrieve        векторный поиск, пул 50 кандидатов (полнотекстовая ветка есть
                   в схеме, по умолчанию с нулевым весом — см. QUALITY.md)
                   параллельно — подбор актуальных фактов по теме
4. rerank          bge-reranker-v2-m3 на сервере: переоценка пар «вопрос↔тред»
5. recency         score × коэффициент свежести (спад с «полом», старое не убивается)
                   → в LLM уходит чистый top-8
6. analyze         GPT-4.1: ответ строго из тредов, до 3 цитат, + поисковые
                   запросы на испанском для проверки
7. web_research    Perplexity: официальные источники (gob.es, gva.es, valencia.es)
8. synthesize      единый живой текст на языке вопроса; опыт чата с цитатами,
                   официальные данные вплетены; даты помечаются
```

**Почему свежесть — множитель, а не сортировка.** Жёсткая сортировка по дате поставит свежий, но нерелевантный тред выше точного ответа годичной давности. Поэтому оценка релевантности умножается на коэффициент свежести со «полом» (старое штрафуется, но не обнуляется) — приём из Onyx.

**Даты идут в промпты.** Модель предпочитает свежее, а на устаревающем (цены, законы, сроки) пишет «по состоянию на такую-то дату».

При любой ошибке — вежливый fallback «сервер занят» на языке пользователя.

### API

```
POST /ask     { question, user_id, platform, lang? } → { answer, sources[], facts_used[] }
GET  /health
```

Ответ содержит источники (ссылки `t.me/...` на треды) — Telegram-бот их приклеивает текстом, мобильное приложение сможет показать карточками.

## 6. Развёртывание

Один `docker-compose.yml` на сервере:

| Сервис | Что |
|---|---|
| `db` | `pgvector/pgvector:pg17` — Postgres 17 + pgvector |
| `models` | эмбеддинги `bge-m3` + реранкер `bge-reranker-v2-m3` на своём железе, ~4 ГБ RAM, GPU не нужен |
| `api` | FastAPI + LangGraph — ядро ответов |
| `bot` | aiogram — Telegram-клиент к API |
| `ingest` | ночной cron-контейнер |

Требования: 2 vCPU / 4 ГБ RAM / 20 ГБ диска — влезает в самую скромную EC2. Бэкап — `pg_dump` по крону.

**Supabase self-hosted не поднимаем.** Из ~10 его сервисов нам нужен только Postgres: агент ходит в базу напрямую по SQL, а не через REST API, как это делал n8n. Гибридный поиск — это обычная SQL-функция, она работает и без Supabase.

### Переключение с n8n

Старый workflow «RAG -FLOW» активен и держит вебхук боевого бота. Порядок: поднять новый стек → проверить на **тестовом** боте → деактивировать workflow в n8n → перевести боевой токен. Не наоборот.

## 8. Открытые вопросы

1. **Сервер:** одна EC2-машина или AWS-аккаунт? От этого зависит, Postgres в docker-compose или RDS. Требование от моделей: ~4 ГБ RAM под эмбеддинги и реранкер, GPU не обязателен.
2. **«Сплетница»** (отдельный workflow в n8n, активен): переносим сейчас или отдельным заходом позже.
3. **Свежесть и слой фактов** заложены в схему, но ещё не проверены замером — первое, что стоит померить после переноса конфигурации в код (см. [QUALITY.md](QUALITY.md)).

Реранкер из этого списка ушёл: выбран self-hosted `bge-reranker-v2-m3`, это подтверждено замером (раунд 3 в [QUALITY.md](QUALITY.md)) — платный Cohere не нужен.
